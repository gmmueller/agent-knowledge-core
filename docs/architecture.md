# Architecture

The public framework contains tools, documentation, briefs and two skeletons (`template/` for persona brains, `template-topic/` for topic brains). The private workspace contains the actual brains and source material. Copy a template to `<workspace>/<name>/`; keep the workspace separate from this repo and never publish it.

When creating a workspace, ask the owner whether to keep a backup and where, such as another drive or an encrypted archive. Keep the workspace off public remotes. Record the choice in the workspace's own notes, including if the owner skips the backup.

## Two kinds of brain

| Kind | Example | Knowledge from | Voice |
|---|---|---|---|
| `persona` (also `course`, `community`) | `my-course` | its own `raw/` | imitates one teacher, with signature phrases |
| `topic` | `my-topic` | the shared `library/` (crawled once per publisher), selected per brain through triage | a specialist with no imitated voice; every quote names its speaker |

Library layout and formats: `docs/library.md`. Item selection: `docs/triage.md`. Topic brains add the page types `example`, `rubric`, `tool` and `debate`, and the rule statuses `consensus` and `contested`.

**Rebuilds.** Library raw, catalogues and `selection.yaml` are inputs. A brain's `wiki/` is a build output tagged `build: { pipeline: N }` in `brain.md`. To rebuild with a better method, build on a branch, run the same `evals.md` on old and new, and merge only if the new one scores at least as well.

## Pieces

| Piece | Where | Role |
|---|---|---|
| Brain folder | `<workspace>/<name>/` | Persona brain: raw sources, wiki and persona card. Topic brain: wiki, selection and ingest working files |
| `brain.md` | Brain folder | Single source of truth for scope, rules, refresh policy and `skill:` settings (trigger text, optional guidance and boundaries). Topic brains also keep their expert lists and evidence types here (see `template-topic/brain.md`) |
| `sources.yaml` | Brain folder | Source registry, titles, access methods, cadence and incremental cursors (persona brains). Topic brains register sources per publisher in the library |
| `crawl.yaml` | Brain folder (optional) | Platform, site, browser port, product mapping, transcription settings and multi-speaker flags |
| `outline.yaml` | Brain folder | Course products, modules, lessons, media ids and attachments |
| `selection.yaml` | Topic brain folder | Library items the brain uses, with a tier and triage scores per item |
| `library/` | Workspace | Shared immutable sources, one folder per publisher, plus `people.yaml` (who speaks where) |
| Generated skill | `<skills-directory>/<name>/` | Thin loader: reads `brain.md` and wiki at use time; broad lookups may use one delegated worker |
| Shared briefs | Framework `briefs/` | Templates for isolated ingest, concept-page and debate-page workers |
| Search | Local qmd collections | Persona brains: `<name>-wiki` and `<name>-raw`. Topic brains: `<name>-wiki`, plus one shared `library` collection |
| Hooks (optional) | Private workspace | Enforce a non-negotiable workflow rule |
| Dedicated persona agent (future) | User's agent directory | Optional named agent wrapper if the user's tooling needs one |

The generator writes `SKILL.md` and `agents/openai.yaml` from `brain.md`. Give `tools/generate_persona.py --brain <path> --out <skills-directory>`, or set `AGENT_KNOWLEDGE_CORE_SKILLS_DIR`. `--out` is the skills **parent** folder: the generator creates `<name>/` inside it, so passing the skill folder itself writes a nested copy. Normal use writes absolute paths; pass `--relative-to <dir>` to write portable paths relative to `<dir>` for a shareable sample skill. Topic-brain skills automatically point at worked examples when `wiki/examples/` has `.md` pages. Distribution into the user's agent tooling is a separate workspace concern. Regenerate after changing `brain.md`; edit the source, never the generated loader.

### Customising a brain's skill

Put anything specific to a brain's subject in that brain's `brain.md`, never in the generator, so the core stays usable for any subject.

The core wording generated by `tools/generate_persona.py` is subject-neutral. It covers loading `brain.md` and `wiki/index.md`, looking up concept and source pages, following the task loop, weighing evidence, citing exact quotes, marking unsupported claims **Inference:**, staying read-only, keeping voices separate and avoiding side effects. For topic brains with `.md` files in `wiki/examples/`, it also adds a pointer to the worked examples automatically.

Add brain-specific instructions in `brain.md` frontmatter under `skill:` (both persona and topic brains support these):

- `skill.guidance:` a list of strings rendered as a `## This brain's guidance` section after "How to use it". Use it for working rules tied to the brain's subject or source mix.
- `skill.boundaries:` a list of strings appended as extra bullets in `## Boundaries`. Use it for subject-specific limits.

When a brain has no `skill.guidance` yet, `generate_persona.py` inspects the brain after writing and prints `consider skill.guidance:` lines for what it finds: official sources in `evidence_types` or `official:`, pages whose `freshness` is other than `evergreen`, pages in `wiki/examples/`, practitioners alongside official sources, and `hosts`. It prints hints only and never writes them for you.

```yaml
skill:
  description: "Consult the my-topic brain: ..."
  short_description: "Cited specialist advice from my-topic"
  default_prompt: "Use $my-topic to answer this, citing sources."
  guidance:
    - "State the capture date on time-sensitive claims and prefer the newest official source."
    - "Worked examples illustrate a method; one case does not generalise."
  boundaries:
    - "**No promised outcomes.** Apply the experts' methods; never promise specific results."
```

What to add, based on a brain's contents:

- **Fast-changing systems (platforms, tools, prices):** name which sources are official, require dates on claims, prefer the newest source, and label practitioner claims about how a system works as their observation.
- **Worked examples (`wiki/examples/`):** state what the examples show and that one case does not generalise.
- **Advice that could be read as a promise of results:** add a `skill.boundaries` bullet against promising outcomes.
- **Interviewers (`hosts:`):** state that their claims never back a rule and how answers should treat them.
- **Writing public content:** add house rules on disclosure, attribution or tone.

## Flow

Persona brain:

```text
sources -> crawl -> raw/ -> ingest -> wiki/ -> extract -> brain.md -> generate -> skill
                                      ^                                      |
                                      +---- file useful answers back <- query+
```

Topic brain:

```text
library (crawl once) -> catalogue -> triage -> selection.yaml -> fetch -> speaker pass
   -> ingest waves -> merge (bundles) -> concept pages -> debates -> rule audit -> draft skill -> evals -> regenerate skill
```

Both flows end the same way: queries that produce something valuable get filed back into the wiki.

## Persona boundaries

A source persona teaches what the expert's material says. The user's own persona skills are separate voices. If a council uses both, each identifies which view it represents. Unsupported advice is marked **Inference:**.

## Ownership and edit guards

| Folder | Who writes it | Rules |
|---|---|---|
| `raw/`, `library/*/raw/` | Capture tools only | Immutable after capture. Neither humans nor wiki agents edit it. Capture writers hash each file (`raw/.capture-hashes.json`, `library/<publisher>/.capture-hashes.json`); `raw_guard.py check` and `lint_wiki.py` fail when they find a changed or missing capture. Fix problems by re-crawling. |
| `wiki/` | Agents during logged passes, humans between passes | `wiki_edits.py` protects human edits. Agents never overwrite a human-edited page; they save a proposal under `ingest/proposals/` instead. |
| `notes/` | Humans only | Agents never create, edit or delete files here. Checks ignore `notes/`; `build_wiki_index.py` lists them under **Your notes**. Notes may link to wiki pages; wiki pages never cite notes as sources. |
| `.obsidian/` | `obsidian_setup.py`, Obsidian and the user | Setup merges defaults into `app.json` and `graph.json` (`--reset` rewrites). Workspace layout files (`/.obsidian/workspace*.json`) are gitignored. |

**Edit detection.** `wiki/.agent-baseline.json` stores SHA-256 hashes of wiki pages. Initialize it once with `wiki_edits.py --brain <brain> record --init`. Start each pass with `begin`, which saves the protected pages and their hashes in `wiki/.agent-pass.json`. `status` reports whether the pass is open. Workers file proposed updates with `propose <page> --from <file> --why "..."`. New proposals mirror their wiki paths under `ingest/proposals/wiki/`, and `proposals` lists both layouts.

`build_wiki_index.py` calls `record` to add agent changes to the baseline and close the pass. If a protected page changed, the pass stays open. Save agent changes as proposals and restore the pre-pass versions. If the owner made the changes, they can acknowledge them with `accept <page>` by naming each page. Then retry the rebuild. Between passes, `record` leaves unexpected differences protected until the owner accepts them.

**Per-core Obsidian vaults:** each brain opens in place as its own Obsidian vault: the brain folder itself, never a synced copy and never `<brain>/wiki/`. Opening the brain folder keeps `brain.md`, `wiki/`, `notes/`, and `raw/` inside one vault; for topic brains, `obsidian_setup.py` adds a `library` directory link (junction on Windows, symlink elsewhere) so `[[library/...]]` citations open the real source files. Each core stays in its own vault because brains can cover unrelated subjects with separate vocabularies, rules and sources, so merging them into one vault or graph mixes unrelated graphs and wikilinks. `obsidian_setup.py --workspace <ws> --all` sets up every brain and writes a small navigation hub vault at `<ws>/.cores-hub/` whose note links each core via `obsidian://open?path=...` (no cross-vault wikilinks; open each core folder once in Obsidian before URI links work from elsewhere).

## Workspace hygiene

Gitignore `.secrets/` at the workspace root, `*/media/` for each brain, `library/*/media/` and `library/*/staging/`, plus `/library` and `/.obsidian/workspace*.json` inside each brain (added by `obsidian_setup.py`) and optionally `/.cores-hub/` at the workspace root (`--gitignore-hub`). Browser profiles, caches and scratch stay in `.secrets/`; course media stays in the brain's `media/`. `raw/` is immutable after capture, `notes/` is human-owned, and `wiki/` and `brain.md` evolve through logged ingests and refreshes.

## Shared-library brains

Topic brains (`kind: topic`) combine experts without imitating one voice. Their citations address `<workspace>/library/<publisher>/raw/`; every quote names its speaker. `check_wiki.py` supports paragraph locators (`@ ¶N`), speaker aliases in `library/people.yaml`, the extra page types (`example`, `rubric`, `tool`, `debate`) and the topic rule statuses (`consensus`, `contested`). A contested rule links to a debate page. See `docs/library.md` for the shared-source design, `docs/triage.md` for selection and `docs/build-pipeline.md` for the topic-brain pipeline and the tool list by stage.

A topic brain finds the library at `<workspace>/library`, where `<workspace>` is the folder that holds the brain. Tools that touch only the library take `--workspace <workspace>`. Tools that work on one brain take `--brain <brain-folder>` and locate the library from it.
